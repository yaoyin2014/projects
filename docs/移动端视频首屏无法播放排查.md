# 移动端视频首屏无法播放排查

## 现象

移动端 H5 视频「首屏大概率无法播放、滚动后才可见反而能播放」，且只在某一台手机复现（其余 4 台正常）。

## 核心矛盾

首屏与滚动后可见的视频走的是不同的渲染路径：

- 首屏视频在页面「初始合成/首次绘制」阶段就渲染并调用 `play()`
- 滚动后才可见的视频，是在页面稳定后、元数据已加载好时才渲染/播放

所以现象只在「首屏失败」说明是**初始化时序问题**，而非 autoplay 策略问题（策略与滚动位置无关）。

## 根因（按概率排序）

1. **`play()` 在 `readyState < 3`（元数据未就绪）时就被调用**，Promise 被 reject；新内核可能静默重试成功，老内核直接失败。
2. **故障机浏览器内核在「初始合成期渲染 video」时有 bug**（尤其微信/QQ 的 X5、UC、国产自带浏览器定制 WebView）：硬件解码 + GPU 纹理分配在首次绘制阶段失败，滚动后「干净地新建」反而正常。
3. **`preload="auto"` 导致首屏视频与图片/JS 抢初始化资源**；滚动视频通常是懒加载，资源空闲才成功。
4. **懒加载/IntersectionObserver 逻辑对「一开始就在视口内」的首屏视频漏处理**（若靠 scroll 事件而非 IO，首屏永不触发）。

## 修复（性价比从高到低）

1. 统一「就绪后再 play + 失败重试」：`readyState >= 3` 才 `play()`，否则监听 `canplay` 再播，`play()` 的 Promise `.catch()` 里重试。
2. 首屏自动播加 `muted playsinline webkit-playsinline preload="auto"`。
3. 首屏视频延迟到 `load` 事件 + `requestAnimationFrame` + `setTimeout(≈100ms)` 后再播，避开初始化竞争。
4. 用 IntersectionObserver（首次回调会对已在视口的元素也触发）替代 scroll 事件判断进入视口。
5. 若源是 HEVC/高分辨率，降级为 H.264 baseline 可救部分机型解码失败。

```js
// 就绪后再 play，并失败重试
function safePlay(video) {
  const tryPlay = () => {
    const p = video.play()
    if (p && p.catch) {
      p.catch(() => {
        if (video.readyState < 3) {
          video.addEventListener('canplay', () => video.play(), { once: true })
        }
      })
    }
  }
  if (video.readyState >= 3) tryPlay()
  else video.addEventListener('canplay', tryPlay, { once: true })
}
```

## 排查第一步

先确认故障机是哪个浏览器/内核版本（是否 X5/老 WebView），再定位是「play 时机」还是「解码/内核」问题。
