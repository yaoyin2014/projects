# 移动端视频首屏无法播放排查

## 现象

移动端 H5 视频「首屏大概率无法播放、滚动后才可见反而能播放」。

复现条件：5 台手机安装**同一个浏览器 APK**（荣耀浏览器，自研内核），**只有 1 台复现**，其余 4 台首屏正常。

实现模式：`poster 占位 → IntersectionObserver 可见 → 触发 video.play()`。

## 核心矛盾

首屏与滚动后可见的视频走的是不同渲染路径：

- 首屏视频在页面「初始合成/首次绘制」阶段就渲染并调用 `play()`
- 滚动后才可见的视频，是在页面稳定后、元数据已加载好时才渲染/播放

所以现象只在「首屏失败」说明是**初始化时序问题**，而非 autoplay 策略问题（策略与滚动位置无关）。

## 关键澄清：自研内核 ≠ 全自包含

浏览器即便内核是 APK 自带的，跑视频时仍要调用手机系统底层的组件：

| 环节 | 谁提供 | 是否跟手机有关 |
|---|---|---|
| 硬件视频解码（H.264/H.265） | 系统 MediaCodec / OMX / 芯片厂商解码器 | 是 |
| GPU 渲染 / 纹理分配 | 系统 EGL / OpenGL ES / Vulkan 驱动 | 是 |
| 画面合成上屏 | SurfaceFlinger / HWC 硬件合成器 | 是 |

内核（Chromium 分支）只是调度者，真正硬解和合成靠以上系统/芯片组件。所以「同 APK + 自研内核 + 只有一台复现」完全成立——问题不在内核代码本身，而在**内核视频渲染路径 × 某款芯片驱动/解码器**的兼容性。

## 收窄后的结论

> 荣耀浏览器内核「首屏视频渲染路径」与**某一款 SoC/GPU/解码器驱动**不兼容的兼容性 bug，只在那个机型上触发。

机制：首屏视频在「初始合成阶段」就要创建硬解 surface + 分配 GPU 纹理，某款芯片驱动在该时点失败；滚动后才渲染的视频是「页面稳定后干净地新建」，避开雷区，所以正常。

## 实测代码模式：poster 占位 + 可见才 play（竞态根因）

`poster 占位 → IO 可见 → play()` 这套实现自带一个竞态：

- 首屏视频在页面加载时就已经「可见」，**IO 首次回调在页面初始化阶段就触发 `play()`**
- 此时视频 `readyState` 还是 0，**元数据都没加载完**
- 滚动后才可见的视频，IO 回调在用户滚动时才 fire，那时元数据早已加载好、页面已稳定

所以「首屏失败」本质是 **`play()` 在元数据未就绪时被抢跑调用**。同一份代码 5 台手机都在抢跑，但故障机内核对「未就绪的 play()」**硬性失败且不自动重试**，其余 4 台内核更宽容。poster 卡住 = `play()` 被拒后无人重试。

## 根因（按概率排序）

1. **`play()` 抢跑（代码侧竞态，主因）**：IO 在页面加载期就触发 `play()`，此时 `readyState < 3`，元数据未就绪。
2. **故障机内核对「未就绪 play()」容错差（内核侧差异点）**：同代码 5 台都在抢跑，只有故障机内核硬失败不重试。
3. **芯片/GPU 驱动在初始合成期渲染 video 失败**：无 poster、或 play 成功后仍不显示帧时，回到这条。
4. **`preload` 未设或为 `none`**：不 play 就不加载元数据，进一步放大抢跑。
5. **懒加载/IntersectionObserver 漏处理「一开始就在视口内」的首屏视频**（若靠 scroll 事件而非 IO）。

## 修复（性价比从高到低）

1. **把「可见就 play」改成「就绪才 play」**（见下方代码）：`readyState >= 3` 才 `play()`，否则等 `canplay`；`play()` 的 Promise `.catch()` 里重试。
2. **`preload="auto"`**：不依赖 play() 就提前加载元数据/数据，让 `canplay` 能及时 fire。
3. 首屏自动播加 `muted playsinline webkit-playsinline`（无手势自动播必须 muted）。
4. 首屏视频延迟到 `load` 事件 + `requestAnimationFrame` + `setTimeout(≈100ms)` 后再播，避开初始化竞争。
5. 用 IntersectionObserver（首次回调会对已在视口的元素也触发）替代 scroll 事件判断进入视口。
6. 若源是 HEVC/高分辨率，降级为 H.264 baseline 可救部分机型解码失败。

```js
// 就绪后再 play，并失败重试
function safePlay(video) {
  const tryPlay = () => {
    const p = video.play()
    p?.catch(() => {
      // 元数据未就绪被拒 → 等 canplay 再试一次
      if (video.readyState < 3) {
        video.addEventListener('canplay', () => video.play(), { once: true })
      }
    })
  }
  if (video.readyState >= 3) tryPlay()
  else video.addEventListener('canplay', tryPlay, { once: true })
}

// 可见 → 交给 safePlay，内部保证就绪后才真播
const io = new IntersectionObserver((entries) => {
  for (const e of entries) {
    if (!e.isIntersecting) continue
    safePlay(e.target)
    io.unobserve(e.target) // 只播一次，避免反复触发
  }
}, { threshold: 0.1 })
```

```html
<video
  muted
  playsinline
  webkit-playsinline
  preload="auto"   <!-- 关键：不依赖 play() 就提前加载，让 canplay 及时 fire -->
  poster="...">
</video>
```

## 排查第一步

对比 5 台手机的**机型 / SoC / Android 版本**，找出故障机与正常机的唯一差异（麒麟/骁龙/天玑，或 Android 版本高低）。故障机临时关硬件加速/硬解，首屏恢复 → 实锤硬解/GPU 路径。同时确认视频的 `muted`、`preload` 属性，以及 `play()` 是否返回被 reject 的 Promise。
